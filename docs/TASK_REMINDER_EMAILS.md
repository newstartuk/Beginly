# Task Reminder Emails

**Date:** 2026-08-30
**Reason:** `sendTaskReminderEmail()` in `lib/email.ts` was fully built (template, copy, brand system) but had zero trigger anywhere in the app — no cron, no scheduled function, nothing reading the `reminder_prefs.email_reminders` toggle Settings already exposed. Users could turn "Email reminders" on in Settings and it was silently a no-op. This closes that gap end-to-end.

## Flow

1. **Vercel Cron** calls `GET /api/cron/task-reminders` once daily (`vercel.json`, `0 9 * * *` — 9am UTC). A single daily invocation is sufficient to correctly serve all four cadences (daily/weekly/biweekly/monthly), since cadence is enforced in the route itself, not by the cron schedule.
2. The route authenticates the request (`Authorization: Bearer <CRON_SECRET>` — Vercel sends this automatically when the `CRON_SECRET` env var is set on the project, same value on both sides) and checks a kill switch (`TASK_REMINDER_EMAILS_ENABLED === "true"`) before doing anything else — see "Kill switch" below.
3. It queries `reminder_prefs` for every row with `email_reminders = true`, joined to `users` for name/email (via the `reminder_prefs.user_id → users.id` foreign key).
4. For each row, `isDue(frequency, last_sent_at)` decides whether enough time has passed since their last reminder for their chosen cadence (`daily` → 1 day, `weekly` → 7, `biweekly` → 14, `monthly` → 28 — see "Cadence approximation" below). A user with `last_sent_at IS NULL` (never reminded) is always due.
5. Due users are capped at `TASK_REMINDER_MAX_PER_RUN` (default 50) per invocation — see "Why a cap" below. Users past the cap simply remain due and get picked up on the next run.
6. For each processed user: `loadPlatformContext()` + `buildJourney()` (the same functions the real Journey Hub UI uses) compute their actual applicable task list; incomplete ones (`journey.tasks` minus `context.completedTaskIds`) become the email's task list and count.
7. Before sending, the route signs a one-click unsubscribe URL for that user (see "Unsubscribe link" below) and picks copy matching their actual `frequency` (see "Frequency-aware copy" below).
8. `sendTaskReminderEmail()` sends via Resend. On success, `reminder_prefs.last_sent_at` is updated to now — on failure, it's left alone so the user is retried on the next run instead of silently skipped for a full cycle.
9. The route returns a JSON summary (`eligible`, `due`, `processed`, `sent`, `failed`, `skippedNoContext`, `cappedAt`) — this is what an audit of a given run should check first.

## Unsubscribe link

Each email includes a real one-click unsubscribe link, not just a pointer to `/settings`. `lib/unsubscribe.ts` HMAC-signs the user id (`signUnsubscribeToken`, same pattern as the existing referral-touch signing in `app/api/platform/onboarding/route.ts` — `createHmac("sha256", secret).update(...).digest("base64url")`), keyed by `TASK_REMINDER_UNSUBSCRIBE_SECRET`. The cron route builds `${siteUrl}/api/unsubscribe?u=<userId>&t=<signature>` and passes it to `sendTaskReminderEmail()` as `unsubscribeUrl`.

`app/api/unsubscribe/route.ts` is the public target — a plain `GET` (so it works as a link clicked from an email client, no session/JS required), verified via `verifyUnsubscribeToken()` (constant-time compare), which sets `reminder_prefs.email_reminders = false` for that user and redirects to `app/unsubscribed/page.tsx` (a small confirmation page, or `?error=invalid_link`/`?error=update_failed` on failure). No login is possible here by design — the signed token is what proves the link is legitimate, since the whole point is that it must work from inside an email.

If `TASK_REMINDER_UNSUBSCRIBE_SECRET` isn't set, `signUnsubscribeToken()` returns `undefined`, the route logs one warning per run (not per user) and sends the email without an unsubscribe link at all — `sendTaskReminderEmail()` falls back to just the `/settings` pointer in that case, so a missing secret degrades gracefully rather than breaking sends.

## Frequency-aware copy

`sendTaskReminderEmail()` now takes an optional `frequency` (defaulting to `"weekly"` if omitted) and adapts: the subject line ("Your Beginly *daily/weekly/fortnightly/monthly* check-in..."), the `<h1>` heading, and the "here are a few to look at *today/this week/over the next couple of weeks/this month*" phrasing, plus the footer's "You received this email because you enabled *X* email reminders" reason line. `biweekly` renders as "fortnightly" for natural phrasing rather than the raw DB value. The cron route passes `row.frequency` straight through from `reminder_prefs`.

## Kill switch

`TASK_REMINDER_EMAILS_ENABLED` must be the literal string `"true"` for any email to actually send — unset, empty, or any other value is a safe no-op (`{ enabled: false }`, no DB query, no Resend usage at all). This was a deliberate, explicit request: leaving the Vercel Cron schedule active costs nothing meaningful on its own, but every real send consumes Resend's send quota, so this flag lets sending be toggled off instantly (via an env var change, no redeploy) while iterating, without touching the cron schedule or route code. **Default posture should be `false`/unset** until the flow has been verified end-to-end against a real account.

## Cadence approximation

`reminder_prefs.frequency` (`daily`/`weekly`/`biweekly`/`monthly`, set in `app/settings/page.tsx`) previously had no backing logic anywhere — this is the first code that reads it. Thresholds are day-counts (1/7/14/28), not calendar-aware (e.g. "monthly" is 28 days, not "the 1st of next month" or a true 30/31-day month) — chosen for simplicity and predictability over calendar precision. Worth knowing if "monthly" ever needs to mean something calendar-exact.

## Why a cap

`TASK_REMINDER_MAX_PER_RUN` (default 50) bounds a single cron invocation two ways: it protects against a Vercel serverless function timeout if the opted-in user base grows large (sends are sequential, each involving a DB read + Resend API call), and it caps worst-case Resend send volume per day. Uncapped users aren't dropped — they're still `due`, just deferred to the next run, so a temporary backlog self-clears over subsequent days rather than compounding.

## Code review pass (2026-08-31)

A review of this branch before commit raised six points. Five were real and are fixed; one was a false alarm, confirmed against the actual schema rather than assumed either way:

- **Fixed** — `TASK_REMINDER_MAX_PER_RUN` wasn't validated: `Number(raw) || DEFAULT` silently ignored an explicit `"0"` (falls back to default instead of respecting "run nobody"), and a negative value like `"-1"` passed straight through into `due.slice(0, -1)`, which drops the *last* element and returns almost everyone — the opposite of a cap — while still reporting `cappedAt: -1` in the response. Replaced with `resolveMaxPerRun()`, which parses as an integer, rejects non-positive/invalid values explicitly (falling back to the default with a logged reason), and only ever returns a valid positive cap.
- **Fixed** — `app/api/unsubscribe/route.ts` cast `userId as string` right before the DB call, papering over the fact that `verifyUnsubscribeToken(userId, token)` returning `true` already proves `userId` is defined, but TypeScript can't see through an opaque function call to know that. Restructured the guard to `if (!userId || !verifyUnsubscribeToken(userId, token))`, so TypeScript narrows `userId` to `string` for everything after the early return — no cast needed, and a future refactor can't accidentally let `undefined` reach the query.
- **Fixed** — `frequency` was typed as bare `string` everywhere (the `sendTaskReminderEmail()` parameter, the cron route's `isDue()`, and both lookup maps), which allowed any string to flow through the whole call chain uncaught. Added `export type ReminderFrequency = "daily" | "weekly" | "biweekly" | "monthly"` in `lib/email.ts`; `FREQUENCY_LABELS`/`FREQUENCY_PERIOD_PHRASES`/`FREQUENCY_DAYS` are now `Record<ReminderFrequency, ...>`, and `sendTaskReminderEmail()`/`isDue()` take `ReminderFrequency` instead of `string`. The one unavoidable cast (`row.frequency as ReminderFrequency`) is now contained to the two points where a raw, untyped `string` from Supabase actually crosses into the typed application boundary, in the cron route — not spread across the codebase.
- **Fixed (docs only)** — `docs/AUTH_EMAIL_TEMPLATES.md` still described the task reminder email as "not wired to any trigger yet" in two places (the trigger table and the "Not done" list) — stale since the cron route was added. Both updated to point at the real trigger and at this doc.
- **Not an issue, verified rather than assumed** — a review comment worried `webhook_events.insert(...)` writes a `signature_verified` column that might not exist, based on this doc's earlier description of a different bug (`payload_fingerprint`/`status`/`event_type` not existing on that table). Checked directly against `supabase/migrations/00000000000000_baseline_snapshot.sql:952` — `signature_verified boolean NOT NULL DEFAULT false` is part of the original baseline schema and was never affected by that bug. No code change made.
- **Accepted as a documented limitation, not fixed** — the cron route fetches *every* `reminder_prefs` row with `email_reminders = true` and filters due-ness in memory, rather than pushing the time-based filtering and `LIMIT` into the query itself. At current scale (a handful of opted-in users) this is irrelevant; it becomes a real cost only once the opted-in population grows large enough that fetching all of it, every day, is itself expensive. The straightforward real fix — a maintained `next_due_at` column (updated alongside `last_sent_at`) that the query can filter and `ORDER BY`/`LIMIT` on directly — is a genuine schema/logic change, not a one-line fix, so it's recorded here rather than done speculatively. See "Not done" below.

## Code review pass 2 (2026-08-31)

A second review raised five more points. Four were real and are fixed; one was a false alarm about a Next.js API this reviewer got backwards for the version actually installed here, verified against Next's own shipped type declarations rather than assumed:

- **Fixed** — both `app/api/webhooks/resend/route.ts` and `app/api/cron/task-reminders/route.ts` compared bearer tokens with a hand-rolled `charCodeAt` XOR loop instead of `crypto.timingSafeEqual`. Extracted a shared `secureEqual()` into [lib/security.ts](../lib/security.ts) (Buffers + `timingSafeEqual`, length-checked first since the function requires equal-length inputs) and pointed both routes at it — one implementation instead of two hand-rolled ones, and it now matches the pattern `lib/unsubscribe.ts`/`app/api/platform/onboarding/route.ts` already used correctly elsewhere in this codebase.
- **Fixed** — `row.frequency as ReminderFrequency` in the cron route trusted the DB value via a type-level cast alone; a genuinely malformed value (typo, legacy data) would silently fall through to the existing `?? "weekly"` fallback with zero visibility. Added `coerceFrequency()`, which validates against the real allowed set and `console.warn`s the specific bad value and user id before defaulting — computed once per row (not once per use-site) so a bad value logs once, not twice.
- **Fixed** — a failed `reminder_prefs.last_sent_at` write after a *successful* send was only `console.error`'d, then silently counted as a normal `sent`. Since `isDue()` reads `last_sent_at` to decide who's due, that user would still show up as due on the next run — a real duplicate-send risk masked as a clean success. Added a distinct `sentButUnrecorded` counter (kept separate from `sent` — the email did go out — and from `failed` — it wasn't a send failure) so this specific risk is visible in the route's own JSON response, not just buried in a log line. Not fixed: an actual idempotency mechanism (optimistic locking, or a `next_due_at`/`last_attempted_at` split) that would prevent the duplicate outright — recorded as future work below, since it's a genuine design decision, not a quick patch.
- **Fixed** — `webhook_events.insert(...)` wrote `signature_verified: true`, but this route only checks a shared bearer secret (`secureEqual`), not a cryptographic signature over the request body (unlike `app/api/auth/send-email-hook/route.ts`, which uses `standardwebhooks`' `Webhook.verify()` for exactly that). Changed to `signature_verified: false` so the audit ledger reflects what was actually checked rather than overstating it.
- **Not an issue, verified rather than assumed** — a review comment claimed `searchParams` in `app/unsubscribed/page.tsx` "is typically passed as a plain object, not a Promise" and that typing/awaiting it as a `Promise` was misleading. That's true for Next.js 14 and earlier, but this project runs `next@15.5.18`, and Next 15's own shipped type declaration (`node_modules/next/dist/server/request/search-params.d.ts`) states explicitly: *"In this version of Next.js the `params` prop passed to Layouts, Pages, and other Segments is a Promise."* This was a deliberate breaking change in Next 15 (the "Async Request APIs" migration). The existing `Promise<{ error?: string }>` typing and `await searchParams` are correct for this installed version; "fixing" it to a plain object would have been a regression. No code change made.

## Not done / open questions for the audit

- **Not yet triggered via the actual Vercel Cron schedule** — verified so far only by calling the route directly (see Testing above). Once deployed, worth confirming a real scheduled invocation fires correctly and `vercel.json`'s cron registered as expected in the Vercel dashboard.
- **`app/unsubscribed/page.tsx`'s rendering not visually confirmed locally** — the unsubscribe *action* (verifying the token, updating `email_reminders`) was confirmed end-to-end; the confirmation page itself has only been read, not seen rendered, since the redirect always lands on `NEXT_PUBLIC_SITE_URL` (production) rather than localhost. Low risk — it's a small static page — but worth a glance once this is actually deployed.
- **The initial `reminder_prefs` query fetches every opted-in row, not just due ones** — due-ness is computed in memory after fetching everything with `email_reminders = true`. Fine at current scale; would need a maintained `next_due_at` column (or per-frequency time-predicate queries) so the database itself only returns rows that are actually due, before this table grows large. See "Code review pass" above.
- **No real idempotency guard against duplicate sends when the `last_sent_at` write fails** — `sentButUnrecorded` (see "Code review pass 2" above) makes this failure mode *visible*, but doesn't *prevent* it: if the DB write keeps failing for a given user across runs, they'll keep getting emailed. A proper fix would be optimistic locking on `last_sent_at`, or splitting `last_attempted_at` (set before sending) from `last_sent_at`/`next_due_at` (set only after a confirmed successful write) — a real design decision, not implemented here.
- **Sequential, not batched, sending** — each due user is processed one at a time (DB read → Resend call → DB write) inside a single function invocation. Fine at current scale; would need batching/concurrency (with a rate limiter for Resend) if the opted-in user base grows substantially, well before hitting a Vercel function timeout becomes likely.
- **Vercel Hobby plan constraint**: Hobby-tier accounts can only run a cron once per day at a fixed time (not configurable to specific hours in the same way Pro allows) — needs confirming which plan this project is on, and whether `0 9 * * *` (9am UTC) is an acceptable fixed time. Not something verifiable from the codebase alone.
- **`email_change`-style double-verification isn't relevant here, but note**: the unsubscribe link's token has no expiry — it's valid indefinitely (as long as `TASK_REMINDER_UNSUBSCRIBE_SECRET` doesn't rotate), since it only proves "this is genuinely a link Beginly sent for this user," not a time-boxed action. Acceptable for an unsubscribe link (industry norm is exactly this), but worth knowing if the same signing helper is ever reused for something more sensitive.
- **Remember to reset `TASK_REMINDER_EMAILS_ENABLED` and `reminder_prefs.email_reminders` for other accounts** back to their intended real-world state before this ships — both were deliberately narrowed down for this local test and shouldn't be left in a "test-only" configuration in a shared project.
