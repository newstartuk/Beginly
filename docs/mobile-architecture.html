Beginly Mobile — architecture reference

The Expo/React Native companion app, mapped from source. It's more architecturally sophisticated than its "never installed" status suggests — an offline-first client with its own security and release-gating layers.

⚠ Never installed or run. The app's own README.md states plainly: "this environment did not install the Expo dependency tree or produce signed Android/iOS binaries." Everything below is a source-level map, not a verified-working map. That's Roadmap Phase 4.

How it talks to the backend

Not a separate API — the mobile app is a client of the same Next.js routes merged into the web project in Phase 0. Default target during development is literally the web dev server:

mobile/lib/api.ts
→
EXPO_PUBLIC_BEGINLY_API_URL
→
defaults to http://localhost:3456

Every request carries a Bearer token (lib/session.ts), an x-request-id, and — for writes — an idempotency key (lib/id.ts). This means mobile inherits the exact same Phase 1 schema gap as web — the same missing tables block both clients identically.

Resilience layers — more built than expected

🔌 Offline-first

  • offline-cache.ts — TTL'd local cache, apiGetCached() serves stale data on failure rather than erroring
  • mutation-queue.ts / mutation-queue-core.ts — failed writes (5xx, timeout, 429) queue instead of failing; background-sync.ts + expo-background-task flush the queue later

🔒 Security

  • SecurityGate.tsx + app-security.ts — gates app usage on device security posture
  • expo-screen-capture — blocks screenshots on sensitive screens
  • expo-local-authentication — biometric unlock available
  • expo-secure-store — session tokens never touch plain storage

📡 Push & deep links

  • push.ts + notifications.ts via expo-notifications
  • deep-links.ts via expo-linking — routes external links into the app's own screens

🚦 Release gating

  • ReleaseGate.tsx + release-policy.ts — can force-block outdated app versions from proceeding, paired with expo-updates for OTA

App composition (app/_layout.tsx)

The root layout wraps every screen in this exact nesting order — worth knowing before touching any of it, since gates are order-dependent:

1AppErrorBoundarycatches render crashes app-wide
2NetworkBannershows a persistent banner when offline
3AppLifecyclewires deep links, push registration, background sync, app-state changes
4Stack (routes)index, login, signup, onboarding, (tabs), settings, support, notifications, referrals
5SecurityGaterendered last — can overlay/block the whole stack
6ReleaseGateoutermost check — forced-update blocking
